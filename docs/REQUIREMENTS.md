# sealform 要件定義書（v0.1 ドラフト）

> 仮称: **sealform**。名前は npm / GitHub の空きを確認してから確定する。
> 作成日: 2026-10-12

---

## 1. 一言でいうと

**Webフォームに入力された内容をブラウザの中で暗号化してから送るライブラリ。** 復号できるのは、秘密鍵を持つ担当者の手元だけ。
サーバー・データベース・ログ・CDN・WAF には暗号文しか残らないので、サーバーが侵害されても入力内容は漏れない。

```html
<script src="sealform.js" integrity="sha384-..." crossorigin="anonymous"></script>
<form action="/contact" method="post" data-sealform-key="/.well-known/sealform-key.json">
  <input name="name">
  <textarea name="consultation" data-seal></textarea>   <!-- この欄だけ暗号化 -->
  <button>送信</button>
</form>
```

暗号の部品（アルゴリズム）は**自作しない**。HPKE（RFC 9180）と、監査済みのライブラリを組み合わせて使う。

## 2. 背景と課題

| 事実 | 意味すること |
|---|---|
| HTTPS で守られるのは**通信経路だけ** | サーバーに届いた時点で平文に戻る |
| 平文はサーバー・DB・アクセスログ・エラー監視（Sentry 等）・バックアップに広がる | 漏えい経路が多い |
| CDN や WAF は TLS を終端するので、事業者側からも中身が見える | 自分で管理しきれない場所に平文がある |
| 問い合わせフォームの漏えい事故は毎年起きている（学校・自治体・医療・士業） | 少人数の組織ほど、サーバーを堅牢に保てない |
| 量子計算機による「今盗んで後で解読」攻撃 | 長く保存する個人情報は、今から耐量子暗号で守る価値がある |

### 守りたい入力の例
相談窓口（いじめ・ハラスメント・健康）、内部通報、採用応募、医療の問診、本人確認書類のアップロード。

### 既存の選択肢との差

| 既存 | 弱いところ | sealform の立ち位置 |
|---|---|---|
| サーバー側での暗号化（DB のカラム暗号化等） | 受け取った瞬間は平文。ログやメモリには平文が残る | **ブラウザで暗号化**するので、サーバーは平文に一度も触れない |
| Tutanota Secure Connect、Proton 等のサービス | 特定のサービスに依存。自分のサイトのフォームには組み込めない | 既存のフォームに **script 1行**で組み込める |
| OpenPGP.js を自分で組み込む | 鍵の配布・形式・UI を全部自作する必要があり、使い方を間違えやすい | 鍵の生成から復号まで**一式**を提供する |

## 3. 想定利用者

| ペルソナ | やりたいこと |
|---|---|
| A. Web 制作者・小規模事業者 | 問い合わせフォームを、手間をかけずに安全にしたい |
| B. 相談窓口・内部通報の運営者 | 相談内容を、サーバー管理者にも見られないようにしたい |
| C. アプリ開発者 | 特定の項目（マイナンバー、病歴など）だけをエンドツーエンドで暗号化したい |

MVP は **A と B** に絞る。

## 4. 脅威モデル

最初に「何から守り、何からは守れないか」をはっきりさせ、README の冒頭にも載せる。

### 守れるもの
| 脅威 | 守り方 |
|---|---|
| サーバー・DB の侵害、バックアップの流出 | 保存されているのは暗号文だけ |
| ログ・エラー監視・解析ツールへの混入 | 送信時点で暗号文になっている |
| CDN・WAF・ホスティング事業者による閲覧 | 同上 |
| 将来の量子計算機による解読 | 耐量子暗号とのハイブリッドで鍵を共有する |
| 暗号文の改ざん・差し替え | AEAD で改ざんを検出し、送信先フォームの識別子を暗号文に結びつける |

### 守れないもの（README に明記する）
| 脅威 | 理由・緩和策 |
|---|---|
| **サーバーを乗っ取られ、配布する JS 自体を書き換えられる** | Web でのエンドツーエンド暗号化に共通する限界。緩和策として SRI、別オリジンからの配信、CSP、公開鍵のフィンガープリント固定、改ざん検知用のブラウザ拡張（v1 以降） |
| 利用者の端末がマルウェアに感染している | 範囲外 |
| 復号担当者の端末・秘密鍵の漏えい | 鍵をパスフレーズで保護し、鍵の更新（ローテーション）を支援する |
| 送信したという事実、送信時刻、データの大きさ | メタデータは隠さない。サイズの丸め（パディング）だけはオプションで提供する |

## 5. スコープ

### やること（MVP）
- ブラウザ用ライブラリ（フォームの指定欄・添付ファイルを暗号化して送る）
- 鍵の生成・公開鍵の配布形式
- 復号ツール（CLI と、オフラインで動くローカル Web アプリ）
- サーバー側の受け取り例（Node・PHP・Python）。サーバー側は暗号文をそのまま保存するだけでよい

### やらないこと
- 暗号アルゴリズムの実装
- 受信データの管理画面・ホスティングサービス（必要なら別プロジェクト）
- 双方向のやりとり（担当者から相談者への暗号化した返信）は v1 以降
- メールでの通知内容の暗号化（通知は「新着あり」だけを送る運用を推奨する）

## 6. 機能要件

### 6.1 ブラウザ用ライブラリ

| ID | 要件 | 優先 |
|---|---|---|
| F-01 | `data-sealform-key` 属性の付いたフォームを自動で検出し、送信時に `data-seal` の付いた欄を暗号化する | Must |
| F-02 | `data-seal` が無い場合はフォーム全体を暗号化する | Must |
| F-03 | 暗号化した欄は、元の name のまま暗号文（base64url の文字列）に置き換えて送る。サーバー側のフォーム処理を変えずに済むようにする | Must |
| F-04 | `<input type="file">` の添付ファイルも暗号化する。50MB までは分割して扱う | Should |
| F-05 | 暗号化の途中で失敗したら、**平文のまま送らずに送信を止める**（フェイルクローズ） | Must |
| F-06 | JavaScript が無効なときは送信できない状態にする（平文が送られる事故を防ぐ）。`<noscript>` で案内を出す | Must |
| F-07 | JS API も提供する（`await sealform.seal(publicKey, data)`）。React 等のフレームワークで使えるようにする | Must |
| F-08 | 送信前に「この内容は暗号化されます」という表示と、公開鍵のフィンガープリントを出せる | Should |
| F-09 | オプションで暗号文の大きさを一定の刻みに丸める（長さから内容を推測されないように） | Could |

### 6.2 暗号方式

| ID | 要件 | 優先 |
|---|---|---|
| F-10 | **HPKE（RFC 9180）** の Base モードを使う | Must |
| F-11 | 鍵共有は **X25519 と ML-KEM-768 のハイブリッド**（X-Wing 方式）。量子でも古典でも、どちらか一方が安全なら安全 | Must |
| F-12 | 共通鍵暗号は AES-256-GCM（Web Crypto の実装を使う）、鍵導出は HKDF-SHA256 | Must |
| F-13 | 暗号文の先頭に版番号と鍵 ID を入れる。将来アルゴリズムを変えても、古い暗号文を復号できるようにする | Must |
| F-14 | 送信先フォームの識別子と送信時刻を**追加認証データ（AAD）**に入れる。別のフォームへの使い回しや差し替えを検出するため | Must |
| F-15 | 暗号部品は監査済みのライブラリだけを使う（例: `@noble/post-quantum`、`@noble/curves`、Web Crypto）。依存は固定し、版の更新は手動でレビューする | Must |

### 6.3 鍵の管理

| ID | 要件 | 優先 |
|---|---|---|
| F-20 | `sealform keygen` で鍵ペアを作る。秘密鍵はパスフレーズで保護したファイル（Argon2id で鍵を導出）として保存する | Must |
| F-21 | 公開鍵は JSON（鍵 ID・アルゴリズム・作成日・有効期限・フィンガープリント）で配布する。置き場所は `/.well-known/sealform-key.json` を推奨する | Must |
| F-22 | 公開鍵の有効期限が切れていたら、ブラウザ側で暗号化を拒否する | Must |
| F-23 | 鍵の更新: 新しい鍵を追加し、古い鍵は「復号専用」として残せる | Should |
| F-24 | 複数の担当者がそれぞれ自分の秘密鍵で復号できる（宛先を複数指定する） | Should |
| F-25 | 秘密鍵の紛失に備えた、紙に印刷できる復旧用コード | Could |

### 6.4 復号ツール

| ID | 要件 | 優先 |
|---|---|---|
| F-30 | CLI: `sealform open <暗号文 | ファイル | CSV>` で復号する。CSV の列を一括で復号できる | Must |
| F-31 | ローカル Web アプリ: 1つの HTML ファイルとして配布し、**ネットワーク無しで**動く。暗号文を貼り付けると復号結果が出る。非エンジニアの担当者向け | Must |
| F-32 | 復号したデータは画面に出すだけで、勝手にファイルに保存しない。保存は明示的な操作でのみ行う | Must |
| F-33 | 改ざんや鍵の不一致を検出したら、理由をはっきり表示する（「別のフォーム宛ての暗号文です」等） | Must |

### 6.5 外からの改ざん監視（新規性の柱）

ブラウザ内で暗号化する方式の最大の弱点は「サーバーを乗っ取られると、配る JS や公開鍵を差し替えられる」こと。
サーバーの中からは気づけないので、**別の場所から定期的に外形を点検する**仕組みを本体に組み込む。既存の Web E2E 暗号ライブラリには無い機能。

| ID | 要件 | 優先 |
|---|---|---|
| F-50 | `sealform check <url>` で公開中のページを取得して点検する | Must |
| F-51 | 配信中の sealform.js の SHA-384 を、**公式の配布物のハッシュ**と照合する。SRI の値ごと書き換えられても検出できるようにする | Must |
| F-52 | 公開鍵の指紋を、登録した値（`--fingerprint`）と照合する | Must |
| F-53 | フォームの設定ミス（GET、送信ボタンの保護漏れ、sealform が外されている）、HTTPS、CSP、SRI の有無を点検する | Must |
| F-54 | 問題があれば終了コード 1。GitHub Actions などで定期実行し、失敗を通知に使えるようにする | Must |
| F-55 | 公式配布物のハッシュを版ごとに記録し、パッケージに同梱する | Must |

### 6.6 配布・連携

| ID | 要件 | 優先 |
|---|---|---|
| F-40 | npm パッケージと、SRI ハッシュ付きの CDN 用ファイル | Must |
| F-41 | サーバー側の受け取り例: Express、Next.js、PHP（素の PHP と WordPress）、Flask | Must |
| F-42 | WordPress プラグイン（Contact Form 7 対応） | Could |
| F-43 | 送信された値が暗号文の形式かをサーバー側で確かめる小さな検証関数（平文の混入を防ぐ） | Should |

## 7. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| N-01 | サイズ | ブラウザ用ライブラリは gzip 後 **60KB 以下**（ML-KEM を含めて） |
| N-02 | 性能 | 一般的なスマートフォンで、10KB のテキストを **100ms 以内**に暗号化する |
| N-03 | 対応ブラウザ | 最新の Chrome / Safari / Firefox / Edge と、iOS Safari 16 以降。Web Crypto が無い環境では送信を止める |
| N-04 | 外部通信 | ライブラリは公開鍵の取得以外に通信しない。テレメトリ無し |
| N-05 | 正しさ | HPKE と ML-KEM は公式のテストベクタで検証する。暗号化・復号はプロパティテスト（ランダムな入力で往復できること）を行う |
| N-06 | 互換性 | ブラウザ版と CLI 版が同じテストベクタを通ること。暗号文の形式は仕様書（`docs/FORMAT.md`）として公開する |
| N-07 | サプライチェーン | 実行時の依存は最小限（目標 3 個以下）。npm には provenance 付きで公開する。リリースごとにビルド成果物のハッシュを公開する |
| N-08 | アクセシビリティ | 送信停止や暗号化の表示はスクリーンリーダーで読み上げられること |
| N-09 | 多言語 | 表示とドキュメントは日本語と英語 |

## 8. 技術構成（案）

| 項目 | 選定 | 理由 |
|---|---|---|
| 言語 | **TypeScript** | ブラウザと CLI（Node）で同じ実装を共有できる |
| 暗号部品 | Web Crypto（AES-GCM、HKDF）、`@noble/post-quantum`（ML-KEM）、`@noble/curves`（X25519）、`hash-wasm` 等（Argon2id） | 監査済みで依存が少ない |
| ビルド | tsup / esbuild | 単一ファイルの出力と、型定義の生成 |
| テスト | Vitest、Playwright（実ブラウザで送信まで確認） | |
| 復号用 Web アプリ | 依存無しの単一 HTML | オフラインで配布できる |

```
sealform/
├── src/
│   ├── core.ts          # 暗号化・復号・暗号文の形式（ブラウザと Node で共通）
│   ├── keyfile.ts       # 秘密鍵ファイル（Argon2id + AES-256-GCM）
│   ├── browser.ts       # フォームへの組み込み（フェイルクローズ）
│   ├── check.ts         # 外からの改ざん監視
│   ├── cli.ts           # keygen / open / check / sri
│   └── opener.ts/.html  # オフライン復号用の単一 HTML
├── test/                # Vitest（happy-dom でフォームの挙動も確認）
├── examples/            # 依存なしの Node サーバー、GitHub Actions の定期点検
├── build.mjs            # esbuild。公式配布物のハッシュを hashes.json に記録
└── docs/                # REQUIREMENTS, FORMAT
```

v0.1 では1パッケージにまとめた。利用者が増えて分ける必要が出たら packages/ に分割する。

## 11. 受け入れ基準（v1.0）

- [ ] 既存の HTML フォームに script 1行と属性の追加だけで組み込める
- [ ] サーバー側のアクセスログ・DB・エラー監視のどこにも平文が残らない（E2E テストで確認）
- [ ] 暗号化に失敗したとき・JS が無効なとき、平文が送信されない（テストで保証）
- [ ] 暗号文を1バイトでも書き換えると、復号時に検出される
- [ ] 別フォーム宛ての暗号文を差し込むと、復号時に検出される
- [ ] ネットワークを遮断した PC で、単一 HTML の復号ツールが動く
- [ ] README の冒頭で「守れないもの」が説明されている

## 12. リスク

| リスク | 対策 |
|---|---|
| 「サーバーが JS を書き換えられる」限界を理解されず、過信される | 脅威モデルを README の冒頭に置き、緩和策の手順も書く |
| 暗号部品の組み合わせ方を間違える | 標準（HPKE）に沿い、独自の構成を入れない。テストベクタと第三者レビュー |
| ML-KEM や X-Wing の仕様・ライブラリが更新される | 暗号文に版番号を入れ、方式を差し替えられるようにする |
| 担当者が秘密鍵を失くして、相談内容を読めなくなる | 複数の担当者を宛先にする、紙の復旧コード、運用ガイド |
| 担当者が復号した平文を Excel 等で雑に扱う | 運用ガイドで「復号後の扱い」を説明する。ツール側は勝手に保存しない |

## 13. 実装状況（2026-10-12 時点・v0.3.0）

機能要件（F-01〜55）はすべて実装した。

| 区分 | 実装 | 補足 |
|---|---|---|
| ブラウザ | F-01〜09 | F-09 は文字列 64 バイト・ファイル 4KB 単位で常に丸める |
| 暗号方式 | F-10〜15 | v0.2 から KEM-DEM 構成の sf2。sf1 は復号のみ |
| 鍵 | F-20〜25 | F-25 は Crockford Base32 の復旧コードと印刷用 HTML |
| 復号 | F-30〜33 | CLI と単一 HTML の両方で、複数の鍵・添付ファイルに対応 |
| 改ざん監視 | F-50〜55 | ハッシュは `npm run release:build` のときだけ記録する |
| 配布・連携 | F-40〜43 | Node・Express・Next.js・Flask・PHP の例、WordPress（Contact Form 7）プラグイン、PHP・Python の検証関数 |

非機能要件:

| ID | 状況 |
|---|---|
| N-01 サイズ | gzip 後 約 23KB（上限 60KB）。CI で上限を超えたら失敗する |
| N-02 性能 | PC のブラウザで 10KB・宛先 2 人の暗号化が中央値 1.7ms。**スマートフォン実機では未計測** |
| N-03 対応ブラウザ | Chromium 系（内蔵ブラウザ）と happy-dom でのみ確認。**Safari・Firefox・iOS Safari は未確認** |
| N-04 外部通信 | 公開鍵の取得以外は通信しない。復号ツールは CSP で通信を遮断 |
| N-05 正しさ | X-Wing は仕様書（draft-10）付録の公式ベクタ 3 件で一致を確認。HPKE 本体（RFC 9180）のベクタは使用ライブラリ側のテストに依存 |
| N-06 互換性 | sealform 独自の復号ベクタ（test-vectors/sealform-sf2.json）と、Node・PHP・Python 共通の検証関数ベクタを用意 |
| N-07 サプライチェーン | 実行時の依存は 3 個（@hpke/core, @hpke/hybridkem-x-wing, @noble/hashes）。provenance 付きで公開する Release ワークフローを用意（**まだ公開していない**） |
| N-08 アクセシビリティ | 状態表示に role=status / alert と aria-live。スクリーンリーダーでの実機確認はしていない |
